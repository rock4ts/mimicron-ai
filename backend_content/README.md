# Mimicron

MVP backend сервиса AI-компаньонов. История каждого диалога хранится в PostgreSQL
и целиком передаётся LLM-провайдеру вместе с описанием личности компаньона
и релевантными долгосрочными воспоминаниями. Воспоминания о пользователе тоже
живут в этой базе: запись принадлежит паре `user_id` + `companion_id`,
деактивируется мягко (`is_active`) и пока не отдаётся наружу HTTP API.
Внутренний `MemoryExtractionService` анализирует существующий диалог, извлекает
структурированные кандидаты через отдельный вызов LLM, а `MemoryManagementService`
сверяет их с активной памятью: дубликаты не накапливаются, устаревшие факты
деактивируются, новые сохраняются. После успешного коммита в PostgreSQL
воспоминание проецируется в Qdrant. Перед ответом
чата текущее сообщение пользователя эмбеддится, Qdrant ищет похожие активные
точки текущего пользователя и компаньона, а канонические строки подгружаются
из PostgreSQL. PostgreSQL остаётся источником истины, Qdrant — только
векторный индекс.

API защищён JWT access-токенами, которые выпускает сервис `backend_auth`.
Компаньоны принадлежат пользователю из claim `sub`; диалоги, сообщения и
воспоминания доступны только через принадлежащего этому пользователю компаньона.

## Требования

- Docker и Docker Compose.
- [uv](https://docs.astral.sh/uv/) — менеджер окружения и зависимостей. Python 3.12
  фиксируется в `.python-version` и ставится через uv при необходимости.
- [just](https://github.com/casey/just) — для запуска тестов.
- Публичный ключ RS256 того же keypair, которым `backend_auth` подписывает access-токены.
  Тестовый публичный ключ лежит в `tests/docker/certs/jwt-public.pem`.

Зависимости описаны в `pyproject.toml`, точные версии — в `uv.lock`.

## Конфигурация

```bash
cp .env.example .env
```

Заполните `LLM_API_KEY`. Для локального запуска без Docker скопируйте публичный ключ:

```bash
mkdir -p certs
cp tests/docker/certs/jwt-public.pem certs/jwt-public.pem
```

Основные настройки:

- `POSTGRES_DB` — имя базы PostgreSQL;
- `POSTGRES_USER` — пользователь PostgreSQL;
- `POSTGRES_PASSWORD` — пароль PostgreSQL;
- `POSTGRES_HOST` — хост PostgreSQL;
- `POSTGRES_PORT` — порт PostgreSQL;
- `LLM_API_KEY` — ключ авторизации LLM-провайдера;
- `LLM_MODEL` — модель LLM-провайдера;
- `LLM_TIMEOUT_SECONDS` — таймаут ответа LLM, по умолчанию `60`;
- `EMBEDDING_PROVIDER` — провайдер эмбеддингов, сейчас только `gigachat`;
- `EMBEDDING_API_KEY` — ключ провайдера эмбеддингов; если пустой, используется `LLM_API_KEY`;
- `EMBEDDING_MODEL` — модель эмбеддингов, по умолчанию `Embeddings`;
- `EMBEDDING_DIMENSIONS` — размерность вектора; ею же конфигурируется коллекция Qdrant;
- `EMBEDDING_TIMEOUT_SECONDS` — таймаут запроса эмбеддинга, по умолчанию `30`;
- `QDRANT_URL` — URL Qdrant, по умолчанию `http://localhost:6333`;
- `QDRANT_API_KEY` — необязательный ключ Qdrant;
- `QDRANT_COLLECTION` — имя коллекции, по умолчанию `memories`;
- `QDRANT_DISTANCE` — метрика расстояния (`Cosine`, `Euclid`, `Dot`, `Manhattan`);
- `QDRANT_TIMEOUT_SECONDS` — таймаут запросов к Qdrant, по умолчанию `5`;
- `MEMORY_RETRIEVAL_TOP_K` — максимум кандидатов семантического поиска, по умолчанию `5`;
- `MEMORY_RETRIEVAL_SCORE_THRESHOLD` — порог релевантности Qdrant, по умолчанию `0.70` для Cosine;
  при Cosine/Dot это минимальный score, при Euclid/Manhattan — максимальное расстояние.
  Смена `QDRANT_DISTANCE` требует перекалибровки порога;
- `MEMORY_MANAGEMENT_TOP_K` — максимум похожих активных воспоминаний при сверке кандидата,
  по умолчанию `10`;
- `MEMORY_MANAGEMENT_SCORE_THRESHOLD` — порог похожести для короткого списка сверки,
  по умолчанию `0.55` для Cosine; те же ограничения диапазона, что у retrieval;
- `LOG_LEVEL` — уровень логирования;
- `JWT_ALGORITHM` — алгоритм проверки JWT, по умолчанию `RS256`;
- `JWT_PUBLIC_KEY_PATH` — путь к PEM-файлу публичного ключа;
- `ROOT_PATH` — публичный префикс за gateway (например `/content/api`); для прямого локального запуска оставляйте пустым;
- `REQUEST_ID_HEADER` — заголовок корреляции, по умолчанию `x-request-id`.

Приложение читает только публичный ключ и не принимает refresh-cookie или
приватный ключ. Production-контейнер не должен получать приватный ключ auth-сервиса:
смонтируйте ту же публичную половину keypair, которой пользуется `backend_auth`.

Все настройки загружаются Pydantic Settings-моделью из `app/config.py`.

## Аутентификация

`backend_auth` отдаёт клиенту пару токенов раздельно: access-JWT в JSON-теле
`{"access": "<jwt>"}`, refresh — в HTTP-only cookie `refresh`. Так работают
`POST /token`, `POST /refresh` и `GET /yandexid/token`. Content API cookie
не читает: клиент берёт значение `access` из тела ответа и передаёт его в
заголовке `Authorization: Bearer <access>`.

Проверка токена локальная: подпись RS256, срок действия `exp` и схема payload
(`sub`, `type=access`, `tv`, `is_superuser`, `iat`, `exp`, `jti`). Сервис не
ходит в БД auth и не сверяет `tv` с `token_version`. После смены пароля или
`POST /logout-others` на auth-сервисе токен остаётся действительным для content API
до истечения `exp` (по умолчанию не больше 30 минут).

Недействительный, просроченный, refresh или повреждённый токен даёт `401` и
заголовок `WWW-Authenticate: Bearer`. `/health` и `/docs` остаются публичными.

Компаньоны создаются с `user_id = sub`. Список, чтение, изменение и удаление
фильтруются по этому UUID. Диалоги и сообщения наследуются через
`conversations.companion_id`. Воспоминания хранят тот же внешний `user_id`
(это не FK в базу auth) и `companion_id`; выборки всегда ограничиваются обоими
полями. Чужой, несуществующий или старый компаньон без владельца
(`user_id IS NULL`) недоступен так же, как отсутствующий ресурс. Claim
`is_superuser` не даёт доступа к чужим данным.

## Архитектура

Каждый HTTP-запрос получает свой Unit of Work (`UnitOfWork`), который оборачивает
SQLAlchemy-сессию. Репозитории принимают UoW и работают с БД через `uow.session`
(add/flush/запросы), но не коммитят. Сервисы принимают только репозитории
(кроме `ChatService`, которому ещё нужен LLM-провайдер и сервис семантического
поиска воспоминаний, и сервисов памяти, которым для индексации, сверки
кандидатов и эмбеддингов нужны LLM, эмбеддинги и Qdrant) и коммитят через
`repository.uow.commit()`. Репозитории компаньонов, диалогов и воспоминаний
получают `user_id` и ограничивают выборки текущим пользователем. `MemoryService`
перед созданием и списком проверяет, что компаньон принадлежит этому
пользователю; чтение, изменение и деактивация воспоминания требуют и
`memory_id`, и `companion_id`. Публичных маршрутов для воспоминаний пока нет.

`MemoryExtractionService.extract_from_conversation` — отдельная внутренняя
способность, не участвующая в генерации ответа чата. Сервис загружает
принадлежащий текущему пользователю диалог, передаёт сообщения LLM в исходном
порядке ролей и требует один JSON-объект
`{"memories":[{"type":"...","content":"...","importance":0.0,"confidence":0.0}]}`.
Ответ модели не доверяется: приложение разбирает JSON и проверяет его
Pydantic-схемами (`extra="forbid"`, `MemoryType`, непустой `content`,
`0.0 <= importance/confidence <= 1.0`). Пустой список кандидатов — успешный
результат без записи в БД. Некорректный JSON, markdown-ограждения, неизвестные
поля, неподдерживаемый тип или значения вне диапазона дают
`MemoryExtractionError` и не создают строк. Сбой или таймаут LLM
пробрасывается как `LLMProviderError` после structured-лога; данные диалога и
воспоминаний не меняются.

Прошедшие валидацию кандидаты не записываются вслепую. Их обрабатывает
`MemoryManagementService`: точное совпадение с активной строкой PostgreSQL
считается дубликатом без второго вызова LLM; остальные кандидаты эмбеддятся,
Qdrant собирает короткий список активных соседей той же пары пользователь/компаньон,
канонические строки читаются из PostgreSQL, затем один вызов существующего LLM
классифицирует пакет как `duplicate`, `update`, `contradiction`, `additional`,
`unrelated` или `discard`. `importance` и `confidence` передаются модели как
ненадёжные сигналы, а не как абсолютная истина. Некорректный план сверки даёт
`MemoryReconciliationError` и не меняет память. Обновление и противоречие
создают новую активную строку и деактивируют старую (`deactivation_reason`
`updated` или `contradicted`, `superseded_by_id` указывает на замену).
Дополнение и новый факт создают строку, не трогая остальные. Дубликат и
`discard` ничего не создают. Неактивные строки в сверку не попадают и не
реактивируются. У созданных строк заполняется `source_conversation_id`.
`companion_id` берётся только из найденного диалога, `user_id` — из текущего
репозитория. Весь пакет мутаций коммитится в PostgreSQL атомарно.

После коммита `MemoryIndexingService` проецирует текущее каноническое состояние:
активная строка — полный upsert с тем же `Memory.id`; неактивная — `is_active=false`
в payload, отсутствующая точка уже согласована. Коммит PostgreSQL и операция
Qdrant не атомарны. Каждая мутация ставит `index_sync_pending=true` в той же
транзакции; успешная проекция снимает флаг отдельным коммитом. Сбой эмбеддинга
или Qdrant оставляет каноническую строку и pending-флаг, ошибка логируется без
содержимого воспоминания. Перед семантической сверкой pending-строки компаньона
повторяются; если активные точки всё ещё не удалось проиндексировать, сверка
прерывается (`MemoryIndexOutOfSyncError`), чтобы не добавить дубликат вслепую.
Индекс чинится командой повторной синхронизации или полной переиндексации.
Удаление компаньона каскадно убирает воспоминания в PostgreSQL и best-effort
удаляет точки Qdrant по `user_id` + `companion_id`.

Перед генерацией ответа `ChatService` вызывает `MemoryRetrievalService`:
один эмбеддинг-запрос по текущему сообщению, один поиск Qdrant с фильтром
`user_id` + `companion_id` + `is_active=true`, `top_k` и порогом score,
затем один batch-запрос PostgreSQL по найденным id. Qdrant-фильтр не заменяет
авторизацию: PostgreSQL повторно проверяет владельца, компаньона и
`is_active`. Содержимое точек Qdrant не считается каноническим. Найденные
воспоминания попадают во второй system-блок промпта как JSON (`type`,
`content`) с явным указанием, что это справочные данные прошлых разговоров,
а не новые инструкции пользователя. Если релевантных воспоминаний нет, блок
опускается. Сбой эмбеддинга, Qdrant или операционная ошибка PostgreSQL на
этапе retrieval логируется, и чат продолжается без памяти; ошибка LLM по-прежнему
даёт `502`. Kafka, гибридный поиск, reranking, граф знаний, фоновые воркеры,
временная БД, сложное забывание и автоматическое извлечение воспоминаний из
чата не реализуются.

`ChatService.send_message` коммитит дважды: сначала сообщение пользователя, затем
ответ ассистента. Если LLM недоступна или не успевает за `LLM_TIMEOUT_SECONDS`,
пользовательское сообщение уже сохранено, ответ ассистента не создаётся, API
возвращает `502`.

После первого успешного ответа ассистента сервис делает второй вызов LLM и
сохраняет короткое русское название в `conversations.title`. Ошибка или пустой
результат этого вызова не меняет ответ API: сообщение ассистента уже сохранено,
`title` остаётся `NULL`, клиент получает `201`. Повторные сообщения название не
перезаписывают.

Сервис принимает входящий `REQUEST_ID_HEADER` (по умолчанию `x-request-id`) или
генерирует UUID и возвращает то же значение в ответе. BFF прокидывает этот
заголовок end-to-end и не отдаёт access JWT в браузер.

## Запуск в Docker

```bash
docker compose up --build
```

Образ собирается через uv по `uv.lock`. Compose монтирует тестовый публичный ключ
в `/app/certs/jwt-public.pem`. Backend применит Alembic migrations после готовности
PostgreSQL и Qdrant и будет доступен по адресу <http://localhost:8000>. Swagger UI —
<http://localhost:8000/docs>. HTML-интерфейс `/ui` сейчас отключён. Qdrant слушает
<http://localhost:6333> в этом compose-файле.

Остановка:

```bash
docker compose down
```

## Локальный запуск

Создайте виртуальное окружение `.venv` и установите зависимости, включая группу `dev`:

```bash
uv sync
```

Поднимите PostgreSQL с Qdrant и запустите приложение:

```bash
docker compose up -d postgres qdrant
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Пересобрать векторный индекс из активных строк PostgreSQL:

```bash
uv run python -m app.commands.reindex_memories
```

Команда пересоздаёт коллекцию Qdrant, заново считает эмбеддинги для
`is_active=true` и upsert-ит точки с тем же `Memory.id`. Успешно проиндексированные
активные строки и отсутствующие неактивные снимают `index_sync_pending`.
Ошибки отдельных записей не останавливают прогон; ненулевой код возврата означает,
что индексация части строк не удалась и команду можно повторить.

Повторить только незавершённую проекцию, не пересоздавая коллекцию:

```bash
uv run python -m app.commands.sync_memory_index
```

После миграции жизненного цикла имеет смысл прогнать одну из этих команд,
чтобы снять pending-флаг у существующих строк и выровнять Qdrant с PostgreSQL.

Новые миграции: `uv run alembic revision -m "описание"`. Имена файлов начинаются
с даты и времени (`YYYY_MM_DD_HHMM_SS`).

Добавление зависимостей:

```bash
uv add <package>
uv add --group dev <package>
```

После изменения `pyproject.toml` обновите lockfile:

```bash
uv lock
```

## Веб-интерфейс

MVP-интерфейс на Jinja2 и HTMX сохранён в репозитории (`app/web`, `app/templates`,
`app/static`), но регистрация HTML-роутера в `app/main.py` закомментирована.
Браузерные переходы не передают `Authorization: Bearer`, поэтому `/ui` обходил бы
проверку JWT. Корневой маршрут `/` перенаправляет на `/docs`.

## Тесты

Тесты используют отдельный `docker-compose.tests.yml` с изолированными PostgreSQL,
Qdrant, тестовым backend и pytest runner. `Dockerfile.tests-app` ставит зависимости
приложения и поднимает API с fake LLM и fake-эмбеддингами; контейнер проверяет
токены публичным ключом из `tests/docker/certs/jwt-public.pem`. `Dockerfile.tests`
ставит зависимости приложения и группы `test`, затем запускает pytest и подписывает
тестовые JWT приватным ключом из `tests/docker/certs/jwt-private.pem`. Оба контейнера
получают настройки из `.env.tests`; pytest читает `TEST_BASE_URL`, `POSTGRES_*`,
`QDRANT_*` и пути JWT через Pydantic Settings в `tests/functional/settings.py`.
Тесты начинаются после применения Alembic migrations и успешного healthcheck backend.

Набор проверяет JSON API, JWT-валидацию, изоляцию данных между пользователями,
внутренний слой воспоминаний (репозиторий/сервис без HTTP), извлечение
долгосрочной памяти из диалога, сверку кандидатов (дубликаты, обновления,
противоречия), индексацию воспоминаний в Qdrant и семантический
поиск с подстановкой релевантных воспоминаний в контекст чата. Вызовы LLM
и эмбеддингов в тестах идут в fake-провайдеры, не во внешний API. Тесты HTML/HTMX в
`tests/functional/testunits/test_web.py` закомментированы, пока веб-роутер отключён.

```bash
just run-tests
```

Команда поднимает тестовый стек, прогоняет pytest и всегда выполняет
`docker compose -f docker-compose.tests.yml down -v`, в том числе при падении тестов.

## API

Публичные маршруты:

- `GET /` — редирект на `/docs`
- `GET /health`
- `GET /docs`

Защищённые маршруты (заголовок `Authorization: Bearer <access>`):

- `POST /companions`
- `GET /companions`
- `GET /companions/{companion_id}`
- `PATCH /companions/{companion_id}`
- `DELETE /companions/{companion_id}`
- `POST /companions/{companion_id}/conversations`
- `GET /companions/{companion_id}/conversations`
- `GET /conversations/{conversation_id}`
- `GET /conversations/{conversation_id}/messages`
- `POST /conversations/{conversation_id}/messages`

Удаление компаньона каскадно удаляет его диалоги, сообщения и воспоминания.
Если LLM недоступна или истекает `LLM_TIMEOUT_SECONDS`, сообщение пользователя
остаётся сохранённым, ответ ассистента не создаётся, а API возвращает `502`.

`GET` и `POST` диалогов возвращают `title` (`string | null`). Название появляется
после успешной обработки первой реплики; до этого и при сбое генерации названия
поле равно `null`.
